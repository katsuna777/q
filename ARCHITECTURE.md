# Отпуска — архитектура

## Стек

| Слой | Выбор | Почему |
|------|-------|--------|
| Ядро | Rust, синхронная библиотека `otpuska-core` | Вся логика — в одном месте и тестируется без окна |
| База | SQLite через `rusqlite` (bundled), WAL | Один файл, без сервера, мгновенный старт, одинаково на macOS и Windows |
| Даты | `chrono` (только `clock`) | `EDATE`/`DATE` ведут себя как в Excel — см. `date.rs` |
| Импорт | `calamine` | Чтение xlsx без Excel |
| GUI | **egui 0.36 + eframe (wgpu)**, `egui_extras` (таблицы), `egui-phosphor`, `rfd` | Тот же стек и тот же вид, что у devbox: чистый Rust, GPU-рендер, без WebView, лёгкий и быстрый |

Данные малы (сотни сотрудников, пара тысяч записей журнала), поэтому **любое изменение сразу пишется в БД и
весь снимок пересчитывается заново** (`Snapshot::build`, доли миллисекунды). Никакого кэша и рассинхрона:
экран всегда рисуется из свежего снимка (`Rc<Snapshot>` в `App`).

## Схема БД (`db.rs`, `PRAGMA user_version = 2`)

```
settings(key, value)                         параметры расчёта и напоминаний; as_of пусто = «сегодня»
departments(id, name UNIQUE, sort)           список подразделений в заданном порядке
employees(id, fio, position, department_id,  department_id → departments, ON DELETE SET NULL
          hire_date, status[work|dismissed|suspended], extra_days, base_days,
          accrual_from, suspend_from, suspend_to, dismiss_date, note)
leaves(id, employee_id, start_date,          employee_id → employees, ON DELETE CASCADE
       base_days, extra_days, note,
       kind[paid|unpaid|maternity|childcare], end_date)       ← схема 2
schedule(id, employee_id, start_date,        график отпусков; ON DELETE CASCADE        ← схема 2
         base_days, extra_days, note)
```

Даты — ISO-текст `YYYY-MM-DD`, дни — `REAL` (допускаются половинки). В отличие от книги, отпуск привязан к
сотруднику по `id`, а не по тексту ФИО: однофамильцы и переименования ничего не ломают.

**Виды отпусков.** Ежегодный (`paid`) задаётся датой начала и днями (`base_days`, `extra_days`) и списывается с остатка.
Остальные виды (`unpaid`, `maternity`, `childcare`) задаются датами «с — по» (`start_date`, `end_date`), в остаток не
входят (`base_days = extra_days = 0`) и требуют обе даты — это проверяют и `Leave::check`, и `Db`.

**Обновление схемы (`Db::open`).** Версия 0 (новый файл) создаётся сразу в схеме 2. Версия 1 (файлы 1.0 и 1.1) обновляется
в одной транзакции: `ALTER TABLE leaves ADD COLUMN kind … DEFAULT 'paid'`, `end_date`, таблица `schedule`, `user_version = 2` —
все прежние строки остаются как были и читаются как ежегодный отпуск. *Перед* этим `copy_before_upgrade` сохраняет в
`backups/otpuska-before-v2-<дата-время>.db` копию в старом формате и проверяет, что она читается; если копии нет — файл не
трогается и открытие завершается ошибкой. Файл новее известной схемы отклоняется. `Db::open_as_is` открывает файл без
обновления (так делается страховочная копия при переходе на несколько баз). Настройки напоминаний — обычные ключи
в `settings`, схемы не меняют. Тесты: `db.rs` (`upgrade_*`, `an_upgraded_file_has_the_same_layout_as_a_new_one`).

## Несколько баз (`databases.rs`)

Список баз лежит в `config.json` (`databases`: `id`, `name`, `path`; `last_db`; `ask_on_start`). Каждая база — свой файл
SQLite со **своей** схемой (`user_version`), поэтому её можно копировать и восстанавливать по отдельности; файл схемы 2
открывает только эта версия и новее, копии «до обновления» — старая тоже. Путь в записи относительный — от папки данных, так что папку можно перенести.

```
Config::migrate        старая установка (одна otpuska.db, config.json без списка) → запись «main» на том же месте
                       + одна страховочная копия backups/otpuska-before-update-….db (в старом формате); файл не трогается
Config::start_choice   какую базу открыть без вопросов: единственную, а при ask_on_start=false — последнюю
create/rename/add_database_file/remove_database/forget_database/open_database
                       проверка названия (не пусто, ≤ 60, без повторов без учёта регистра); удаление переносит файлы
                       в deleted/ (purge_deleted стирает через 30 дней); отсутствующий файл не создаётся заново
Db::peek               сколько сотрудников/записей в файле (только чтение) — для списка баз
```

Список баз доступен и из рабочего окна: кнопка с названием базы в боковой панели (`App::db_chip`) открывает всплывающий
список (число сотрудников читается `Db::peek` один раз, при открытии списка); выбор вызывает `App::switch_database`, которая
отказывается закрывать базу, пока в карточке сотрудника или в «Настройках» есть несохранённый ввод (`unsaved_work`).

Окно (`otpuska-gui/src/launcher.rs`): `Root` показывает либо `Chooser` (выбор базы), либо `App` (работа с открытой базой).
Смена базы закрывает `App` вместе с соединением SQLite и открывает другой — состояние экранов, фильтры и снимок не
переходят из одной организации в другую. Автокопия за день делается при открытии каждой базы, в её собственную `backups/`.

## Правила расчёта (`engine.rs`) и где они были в книге

| Книга | Код |
|-------|-----|
| `Сотрудники!V` — начало отсчёта (приём или «Учёт с» + сдвиг на приостановку ТД) | `compute` → `accrual_base` |
| `Y`, `Z`, `AA` — полных лет, начатых и доступных периодов (первый — через N мес.) | `years`, `started`, `available` |
| `AB`/`AC`, `AD`/`AE` — отгуляно и остаток отдельно по основному и доп. отпуску | `taken_*`, `left_*` |
| `AF`…`AJ` — самый ранний период с остатком, крайний срок, дней до срока | `early_period`, `deadline()`, `days_left()` |
| `K` — состояние | `State`, `compute` (порядок проверок тот же) |
| `AL` — ключ сортировки «Сводки» | `State::rank` + `Snapshot::summary_order` |
| `Периоды` — 8 лет подряд, остаток и срок по каждому году | `period`, `period_for_year` |
| `Журнал` — окончание, статус, остаток | `leave_end`, `leave_status` |
| `Отчёты` — ближайшие отпуска и сводка по подразделениям | `Snapshot::upcoming`, `dept_report` |
| (нет в книге) отпуск без оплаты свыше 14 дней и по уходу за ребёнком сдвигают рабочий год | `WorkYear`, `build_years`, `walk` |
| (нет в книге) график отпусков, напоминания | `schedule.rs` |

**Рабочие годы с отпусками, которые не идут в стаж** (`engine.rs`). Год k начинается в «юбилей» даты начала отсчёта
(`EDATE(начало, 12·(k−1))`, как в книге) плюс число дней, на которое сдвинуты все прошлые годы. Конец года находит `walk`:
идёт по дням вперёд, пока не наберётся столько «засчитываемых» дней, сколько в номинальном году (365 или 366). День отпуска
по уходу за ребёнком не засчитывается никогда, день отпуска без оплаты — только если это не первые 14 таких дней в году;
дни считаются по календарю, поэтому записи, которые пересекаются, и отпуск на стыке двух лет учитываются верно, а лишние дни
внутри уже продлённого года тоже не считаются. Сдвиг года = `конец − номинальный конец`; следующий год начинается на
следующий день. Крайний срок периода = `EDATE(начало, 12·k + срок) − 1` плюс накопленный сдвиг. Без таких отпусков все даты
в точности прежние — это проверяет тест `without_such_leave_every_date_is_what_the_old_formulas_gave` (формулы версии 1.0 внутри теста,
29 февраля, конец месяца) и сверка расчёта на базе из 113 и на 320 синтетических сотрудниках (`examples/baseline.rs`).
Право на первый отпуск (6 месяцев) сдвигается так же (`first_available`). Декретный отпуск в стаж засчитывается — в движок
как промежуток не передаётся.

**График и напоминания** (`schedule.rs`). Запись графика «выполняется» записью журнала того же сотрудника с пересекающимися
датами (каждая запись журнала — одной записью графика, ближайшей по началу). Статус: `Ahead` / `Booked` / `InLeave` / `Done` /
`Missed`. Напоминания (`Snapshot::reminders`, считаются при каждой сборке снимка): начало ежегодного отпуска из журнала и
записи графика без отпуска в журнале — в два срока (по умолчанию 14 дней и 1 месяц), запись графика с прошедшей датой без
отпуска в журнале (30 дней), окончание отпусков по беременности и родам и по уходу за ребёнком (14 дней). Сроки — в настройках.

Проверка: расчёт сверен с пересчётом формул самой книги (движок `formulas` на демо-книге: 18 сотрудников,
144 ячейки «Периодов», счётчики «Сводки») — расхождений нет. Крайние случаи (29 февраля, пороги 90/180 дней,
приостановка, доп. отпуск, записанный как основной) покрыты тестами в `engine.rs`.

## Модули `otpuska-core`

```
date         EDATE/DATE как в Excel, разбор и вывод дат дд.мм.гггг
model        Employee, Leave (+ LeaveType), Plan, Settings, Params, Status
engine       compute / compute_with, period, WorkYear, Snapshot (сводка, отчёты, предупреждения)
schedule     график отпусков против журнала, напоминания
db           SQLite: схема, CRUD, замена всех данных (импорт), копия, проверка файла
config       пути (OTPUSKA_HOME), config.json, ежедневная автокопия, восстановление
databases    список баз (по одной на организацию), миграция с версии 1.0, создание/переименование/удаление
xlsx_import  чтение старой книги по заголовкам колонок
filter       фильтры сводки, сотрудников, периодов, журнала, графика, напоминаний и отчётов: одни и те же строки для экрана и печати
print        печатные отчёты (самодостаточный HTML) по готовому списку строк и описанию фильтров
```

## Модули `otpuska-gui`

```
launcher   корень окна: выбор базы при запуске, смена базы
app        состояние, действия над БД, оболочка (боковая панель, шапка, уведомления)
theme      палитры (чёрная тёмная, светлая, 5 акцентов), шрифт Inter
ui         виджеты: кнопки, плашки состояний, карточки, поле даты с календарём, выбор
           сотрудника с поиском, таблицы
platform   открыть файл / показать в папке на macOS, Windows, Linux
views/     summary, employees, employee (карточка), periods, journal, schedule, reminders, reports, settings
```

**Экран и печать берут строки из одного места** (`filter.rs`: `emp_rows`, `summary_rows`, `period_rows`, `leave_rows`).
Экран сортирует этот список и рисует его, кнопка «Печать» передаёт в `print::*` тот же список вместе с описанием
фильтров — поэтому напечатанное совпадает с показанным; это проверено тестами (`tests.rs`: нажатие «Печать» при
включённых фильтрах).

Модальных окон нет: каждый сценарий — вкладка или карточка в главном окне. Удаление — в два клика
(первый «заряжает» кнопку).

## Производительность и платформы

Измерено на Mac (Apple Silicon), сборка `--release`, база из 320 сотрудников и 871 записи журнала:

| Что | Время |
|-----|-------|
| Полный пересчёт после правки (`Snapshot::build`) | 0,98 мс (3200 сотрудников — 9,7 мс) |
| Чтение базы (`Db::load`) | 0,5 мс |
| Построение кадра любого экрана (раскладка и команды рисования, без GPU) | 0,1–0,3 мс |
| Запуск до первого кадра | 110–130 мс (холодный кэш — до 300 мс) |
| В простое | 0 кадров, 0% CPU; память ≈ 96 МБ |

Узких мест в данных и раскладке нет, поэтому кэшей и фоновых потоков нет: каждое изменение пересчитывает всё. Экраны
рисуются «по требованию» (egui перерисовывает только после ввода или анимации); это проверяет тест `idle_repaint_scan`
(указатель над каждым экраном по сетке точек — кадры должны прекращаться). При движении мыши окно занимает порядка
10–20% одного ядра — это стоимость отрисовки на GPU, а не расчётов.

Платформы: сочетания клавиш — `Cmd` на macOS и `Ctrl` в Windows (`egui::Modifiers::COMMAND`); шрифты встроены (Inter), от
системных не зависят; печатные отчёты открываются браузером по умолчанию (`open` / `rundll32 url.dll,FileProtocolHandler` /
`xdg-open`); база и `config.json` — в локальной, не сетевой папке; окно подгоняется под экран (`launcher::fit_to_screen`).
Windows собирается и проверяется на CI (`.github/workflows/build.yml`); локально на Mac его собрать нельзя.
